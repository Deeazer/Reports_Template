# Интеграция с Yonote

Приложение умеет импортировать данные из базы знаний **Yonote** (yonote.ru).
Yonote построен на Outline, поэтому используется совместимое с Outline API
(POST-методы `/api/<группа>.<действие>`, авторизация Bearer-токеном, документы
в Markdown).

Поддерживаются два сценария:

1. **Импорт уязвимостей** — один документ Yonote = одна готовая уязвимость.
   Основной сценарий: вы ведёте уязвимости отдельными документами в дереве
   коллекции, а приложение импортирует их в выбранный проект и вид работ.
2. **Импорт проекта целиком** — один документ-«карточка проекта» с уязвимостями
   в теле (запасной вариант, см. ниже).

## Настройка

**Адрес пространства** задаёт администратор один раз, **API-токен —
персональный у каждого пользователя** (импорт идёт под токеном того, кто его
запустил, и видит только доступные этому пользователю документы).

1. Администратор: **Настройки → Интеграция с Yonote** → заполните **Адрес
   Yonote** (например `https://cyberbits.yonote.ru`) и, при желании, коллекцию
   по умолчанию (**Загрузить коллекции** → выбрать → **Сохранить**).
2. Каждый пользователь: в Yonote **Настройки → API-токены** создаёт свой токен,
   затем в приложении **Настройки → Интеграция с Yonote** вставляет его в поле
   **Ваш API-токен** и нажимает **Сохранить**. Кнопка **Проверить подключение**
   покажет, под какой учётной записью Yonote работает импорт.

Токены хранятся на сервере по пользователям и наружу не отдаются. Импорт
уязвимостей доступен всем пользователям, у которых есть доступ к проекту;
настройку общего адреса и коллекции меняет только администратор.

## Сценарий 1. Шаблон документа-уязвимости

**Один документ Yonote = одна уязвимость.** Заголовок документа — название
уязвимости (ведущий значок/эмодзи, например 🔴, отбрасывается).

Поля в начале документа можно оформить **двумя способами — оба работают**:

- **Простыми строками «Поле: значение»** (по строке на поле; можно списком
  через «- ») — самый надёжный способ, не зависит от блоков Yonote;
- **таблицей** из двух колонок «поле | значение» (как в текущих отчётах).

Ниже полей — текстовые блоки (PoC, результаты, рекомендации) под заголовками
`## …`. Пример простым текстом:

~~~markdown
Вид работ: внутренний
Описание: Неаутентифицированный доступ к MongoDB на внутреннем периметре.
Границы: 10.105.5.24, 10.105.5.102
Инструменты: nmap, mongosh
Обнаружена: 03.11.2026 11:05
Модели нарушителя: Н2
CVSS: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:L

## Proof of Concept
mongosh "mongodb://10.105.5.24:27017" --eval "db.adminCommand('listDatabases')"

## Рекомендации
Включить аутентификацию, ограничить доступ к порту 27017.
~~~

Тот же документ таблицей:

~~~markdown
| Вид работ | internal |
| Описание | В ходе тестирования внутреннего периметра выявлена уязвимость… |
| Границы | 10.105.5.24, 10.105.5.102 |
| Инструменты | nmap, Metasploit |
| Обнаружена | 03.11.2026 11:05 |
| Модели нарушителя | Н2 |
| CVSSv3.1 | AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:L |

## Proof of Concept
```
nmap -p445 --script smb-vuln-ms17-010 10.105.5.0/24
```

**Результаты эксплуатации:** получен доступ с правами NT AUTHORITY\SYSTEM.
**Рекомендации:** установить MS17-010, отключить SMBv1.
~~~

### Поля таблицы

| Метка в Yonote | Поле уязвимости |
|---|---|
| Вид работ | вид работ (`internal`, `external`, `web`… или название; если не указан — берётся выбранный при импорте) |
| Описание | описание |
| Границы | границы |
| Инструменты | инструменты |
| Обнаружена | время обнаружения |
| Модели нарушителя | модели нарушителя |
| CVSS / CVSSv3.1 / вектор | вектор CVSS v3.1 |
| OWASP | категория OWASP Top 10 (для веб) |
| WSTG | категория OWASP WSTG (для веб) |
| Рекомендации | рекомендации |
| Результаты эксплуатации | результаты эксплуатации |

**Вектор CVSS** распознаётся автоматически в любой строке таблицы — и если он
стоит в отдельной строке без метки (как в существующих отчётах, где над ним
идёт строка «CVSSv3.1 | 8.6» с числовой оценкой). Префикс `CVSS:3.1/`
необязателен. Числовая оценка и «Опасность» игнорируются — приложение
считает критичность само из вектора.

> **Итоговый риск** (таблицы 1.4/3) дополнительно требует «Доступность уязвимой
> функциональности» и «Простоту эксплуатации» — их в документе Yonote нет, их
> нужно указать в карточке уязвимости после импорта. Критичность по CVSS
> вычисляется сразу.

### Текстовые блоки (ниже таблицы)

Длинные поля можно оформлять либо строкой таблицы, либо блоком в теле —
заголовком `## Метка` или жирной меткой `**Метка:**`, текст идёт до следующей
метки/заголовка:

| Метка | Поле |
|---|---|
| Описание | описание |
| PoC / Proof of Concept | Proof of Concept |
| Результаты эксплуатации | результаты эксплуатации |
| Рекомендации | рекомендации |

Если под таблицей нет ни меток, ни заголовков — весь текст считается PoC.

### Как импортировать

На странице проекта откройте нужный вид работ (например «Внутренний пентест»)
и нажмите **«Импорт из Yonote»**. В окне раскройте дерево коллекции до папки с
уязвимостями (например `УЯЗВИМОСТИ → Int_vuln`), отметьте нужные документы и
нажмите импорт — каждый выбранный документ станет уязвимостью выбранного вида
работ.

### Рекомендованная структура дерева в Yonote

```
Коллекция
└─ Проекты
   └─ <Проект>            (напр. КИТ-ФИНАНС)
      ├─ Внешка / Внутрянка        (описание/скоуп вида работ)
      └─ УЯЗВИМОСТИ
         ├─ Ext_vuln      (документы-уязвимости внешнего пентеста)
         └─ Int_vuln      (документы-уязвимости внутреннего пентеста)
```

Папки нужны только для вашего удобства — при импорте вы сами выбираете, в какой
вид работ проекта попадут отмеченные документы.

## Сценарий 2. Импорт проекта целиком

Если удобнее держать проект одним документом, поддерживается и это: **Проекты →
Импорт из Yonote**. Один документ верхнего уровня = один проект; заголовок —
название проекта, тело — Markdown:

```markdown
## Карточка
- Заказчик: АО «Экопром»
- Период: 01.10.2026 — 20.10.2026
- Виды работ: external, internal, web
- Описание объекта: …

## Уязвимости
### Обход авторизации
- Вид работ: external
- CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
- Границы: admin.example.com
**Описание:** …
**Рекомендации:** …
```

Поля «Карточки»: Заказчик, Реквизиты, Описание объекта, Технологические участки,
Период, Виды работ. Каждая `### …` в разделе «Уязвимости» — отдельная уязвимость
с теми же полями, что и в сценарии 1.

## Картинки

Скриншоты из блоков **Proof of Concept** и **Результаты эксплуатации**
переносятся в карточку уязвимости автоматически: при импорте приложение
скачивает каждое изображение из Yonote (под вашим токеном) и прикрепляет к
соответствующему блоку, а ссылку убирает из текста. Подпись к рисунку берётся
из альтернативного текста картинки, если он задан. Недоступную картинку импорт
пропускает, не прерывая остальной перенос.

## Что НЕ переносится

Вложения-файлы (не картинки) и картинки из других блоков, кроме PoC и
результатов эксплуатации, не переносятся. Границы проекта (Приложение 1),
нарушители и каталог угроз берутся из справочников по умолчанию; «Доступность»
и «Простота эксплуатации» заполняются в приложении.
